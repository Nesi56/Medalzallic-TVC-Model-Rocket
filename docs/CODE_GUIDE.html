Structure

How the files talk to each other

The design is a hub with spokes. TVC_Flight_Computer.ino is the only file that makes decisions. Every .h file is a toolbox: it holds one job (read a sensor, estimate tilt, drive the servos, time the landing burn) and waits to be called. The headers never call each other's functions. They only share the settings in config.h and the math in flight_types.h.

So if you want to know when something happens, read the .ino. If you want to know how it's done, open the header it calls.

Timing

One trip around the loop, every 2 ms

Arduino calls loop() as fast as it can. The first thing it does is check for typed commands, then it waits until 2 ms have passed since the last pass (LOOP_HZ 500). Then it runs these steps in this exact order, 500 times a second. Slower jobs ride along by counting passes: the barometer gives a new reading every 10th pass, the log saves every 5th, telemetry goes out every 50th.

  1. pollStream(Serial) · pollStream(GROUND_SERIAL)Collects typed characters from USB and the ESP32. A full line (ending in Enter) goes to handleCommand().
    every pass.ino
  2. wait for the 2 ms tick, measure dtdt is the real time since the last tick (about 0.002 s). Every integration below uses it.
    500 Hz.ino
  3. sim.step(dt, gimbal, pyro flags)Only in SIM_MODE 1: moves the virtual rocket forward 2 ms using the gimbal angles the code commanded last pass.
    500 Hzsim.h
  4. readImu()Reads 14 bytes from the MPU6050 (or the sim), converts to g and °/s, and remaps the chip's axes to rocket axes with IMU_AXIS_FOR_BODY_*.
    500 Hzimu_mpu6050.h
  5. att.update(gyro, accel, dt)Turns the attitude estimate by the measured rotation. On the ground it also nudges the estimate toward gravity so it can't drift.
    500 Hzattitude.h
  6. accUp = att.verticalAccel(accel)Acceleration straight up, with gravity removed. During coast and descent anything over 1 g is a shock (the E16-4 ejection charge) and is replaced with plain free fall.
    500 Hzattitude.h.ino
  7. nav.predict(accUp, dt)The altitude filter's fast step: velocity += accel × dt, altitude += velocity × dt.
    500 Hznav_filter.h
  8. pollBaro() → nav.updateBaro(baroAlt)If the BMP388 has a new sample, convert pressure to altitude and use it to correct the filter's drift.
    50 Hzbaro_bmp3xx.hnav_filter.h
  9. nav.reset(0) while sitting on the padOn the ground the rocket is at 0 m and 0 m/s by definition, so the filter is pinned there until thrust shows up.
    500 Hznav_filter.h
  10. readVoltages()Pyro-rail voltage (is the ARM switch on?) and igniter continuity through the resistor dividers.
    10 Hzpyro.h
  11. runStateMachine(dt, now)The decisions. Depending on the state it steers the gimbal, checks for lift-off, burnout or apogee, asks landing.h whether to fire, or fires a pyro channel.
    500 Hz.inotvc.hlanding.hpyro.h
  12. pyroAscent.update() · pyroLanding.update() …Turns each igniter off once it has been on for PYRO_FIRE_MS (1 s).
    500 Hzpyro.h
  13. logRecord(now)Copies 18 numbers into the RAM flight log (64 bytes per record, 40 seconds kept).
    100 Hzflight_log.h
  14. sendTelemetry(now)Sends one T,… line to the ESP32 (and to USB when not idle).
    10 Hz.ino
  15. updateIndicators(now)LED and buzzer patterns for the current state: armed chirps, countdown beeps, locator beeps after landing.
    500 Hz.ino

attitude.h · flight_types.h

Tilt: knowing which way is up

The MPU6050 gyro measures how fast the rocket is rotating, in °/s, about its own three axes. AttitudeEstimator adds those small rotations up 500 times a second into a quaternion q: four numbers that describe which way the rocket is pointing without the gimbal-lock problems of plain angles. qintegrate() in flight_types.h does the adding.

From q the code asks one question: where is "world up" as seen from the rocket? That vector is upInBody(). Its sideways parts become tiltXDeg() and tiltYDeg(), the tilt about each gimbal axis. Because the tilt is measured in the rocket's own axes, it stays correct when the rocket rolls.

Why calibration matters. On the ground the accelerometer feels gravity, so the code uses it to keep the estimate honest. In flight it feels thrust and drag instead, so the code switches it off and trusts the gyro alone. Any gyro error then piles up: a 0.5 °/s bias becomes a 5° tilt error after 10 s. That is why ARM makes you keep the rocket still for 2 s while it measures the bias.

// attitude.h, update(): every 2 ms
Vec3 w = (gyroDps - gyroBiasDps) * DEG2RAD;
if (useAccel) {               // ground only
  Vec3 err = cross(normalized(accelG), upInBody());
  w = w + err * 2.0f;         // nudge toward gravity
}
q = qintegrate(q, w, dt);

// tilt about each gimbal axis
float tiltXDeg() { Vec3 u = upInBody();
                   return atan2f(u.y, u.z) * RAD2DEG; }
float tiltYDeg() { Vec3 u = upInBody();
                   return atan2f(-u.x, u.z) * RAD2DEG; }
nav_filter.h · baro_bmp3xx.h

Altitude: predict fast, correct slowly

Two sensors know something about height, and each is bad in its own way. The accelerometer is smooth and instant but drifts, because adding up acceleration twice turns tiny errors into big ones. The BMP388 barometer never drifts but is noisy and only updates 50 times a second.

AltitudeFilter is a Kalman filter that combines them. Every 2 ms predict() moves altitude and velocity forward using the accelerometer. Every 20 ms updateBaro() compares the prediction with the barometer and pulls it part of the way back. How far it pulls depends on how much the filter currently trusts each source. It also tracks the accelerometer's bias as a third number. A barometer reading more than 4 m away from the prediction is treated as a glitch and ignored (gateM).

tvc.h

Gimbal control: push the tail back under the nose

During the two burns, runStateMachine() calls tvc.update(tiltX, tiltY, rateX, rateY, dt, true) every 2 ms. Each axis is a PID controller whose output is a gimbal angle:

gimbal = KP × tilt  +  KI × ∫tilt dt  +  KD × tilt_rate
         = 0.40 × tilt + 0.10 × ∫tilt  + 0.12 × rate

KP pushes back harder the further it leans. KD pushes against the turning speed so it doesn't overshoot. KI slowly builds up a correction for a constant lean, such as a motor mounted slightly crooked or the CG off-centre.

Worked example from the code's own numbers: tilt 2°, turning at 3 °/s, no built-up integral. Gimbal = 0.40 × 2 + 0.12 × 3 = 1.16°. setGimbal() multiplies by GIMBAL_TO_SERVO_RATIO (3) and SERVO_US_PER_DEG (10): 1.16 × 3 × 10 ≈ 35 µs, so the servo pulse goes from 1500 to 1535 µs. servoWriteUs() then sets the Teensy's hardware PWM to 2,515 counts out of 32,768 at 50 Hz.

The total deflection is capped at TVC_MAX_GIMBAL_DEG (5°) and the integral at 2°, so a stuck sensor can't drive the mount into its stops.

landing.h · motor_curves.h

Landing timing: when to light motor 2

A solid motor can't be throttled or turned off, so the one thing the computer controls is the moment the igniter gets power. In DESCENT, every 2 ms, landingFireDecision() runs two quick simulations from the current altitude and speed:

"If I fire now" and "if I fire one loop later". Each one plays out the igniter delay (free fall for 0.35 s), then the E16 thrust curve with the rocket getting lighter as propellant burns, drag, touchdown, and any hop back up on leftover thrust. Each returns the worst touchdown speed. The code fires the first moment that waiting would make the touchdown harder.

Why your igniter delay matters so much. The prediction assumes the motor lights exactly IGNITER_DELAY_S after power-on. If the real igniter is faster or slower, the motor effectively lights at the wrong height. The table shows what happens to a 1.1 kg rocket when the real delay differs from the setting.

That's why the log records LANDING MOTOR LIT x s after fire on every flight: it is your measured delay. Put the average back into config.h.

pyro.h · TVC_Flight_Computer.ino

Pyro safety: every gate must be open

An igniter only gets current if the physical ARM switch is on and the software lets the MOSFET turn on. The software side is four separate checks inside PyroChannel::fire() and the state machine. If any one of them says no, the pin stays LOW.

Other automatic disarms. The code also drops back to IDLE with pyros off if the rocket tips more than 10° on the pad, the ARM switch is turned off, 10 minutes pass without a launch, or (for a countdown started from the phone) the Wi-Fi heartbeat stops for 2 s. A misfire disarms and tells you to wait 60 s before approaching.
USB · Serial2 · ESP32

Talking to the rocket

Everything goes over plain text lines. Commands go in, two kinds of lines come out: T, telemetry 10 times a second, and M, messages whenever something happens. The ESP32 just relays them: it turns the phone's button presses into command lines on its UART (GPIO17 to Teensy pin 7) and serves the Teensy's lines (pin 8 to GPIO16) to the web page.

Study plan

Read the code in this order

  1. config.h: skim every setting so you know what knobs exist.
  2. TVC_Flight_Computer.ino, setup() and loop() (lines 722–846): the heartbeat. Match it against the loop list above.
  3. runStateMachine() (line 338): one case per state. Keep the state diagram open beside it.
  4. handleCommand() (line 555) and tryArm() / finishCalibration() (lines 270–336): how a command becomes action, and what ARM checks.
  5. attitude.h, with qintegrate() and qrotateInv() from flight_types.h: tilt.
  6. nav_filter.h: altitude and velocity. Read predict() then updateBaro().
  7. tvc.h: 62 lines, the PID and the servo conversion.
  8. landing.h: predictIgnitionNow(), then landingFireDecision().
  9. pyro.h: short, but read every line before you connect an igniter.
  10. imu_mpu6050.h and baro_bmp3xx.h: only needed when you're wiring real sensors.
  11. sim.h, flight_log.h and ESP32_Ground_Link.ino: when you want to change the virtual rocket, the log, or the phone page.
Setup

Getting it into the Arduino IDE

  1. Install Arduino IDE 2. In File → Preferences → Additional boards manager URLs add https://www.pjrc.com/teensy/package_teensy_index.json, then install Teensy from the Boards Manager.
  2. Get the files: unzip the download, or clone the GitHub repository. Don't use Sketch → Include Library → Add .ZIP Library: that menu is for libraries, and this is a sketch.
  3. Move the TVC_Flight_Computer folder into your sketchbook (Documents/Arduino). Keep the folder name: Arduino requires it to match TVC_Flight_Computer.ino.
  4. File → Open → TVC_Flight_Computer.ino. All 13 files open as tabs across the top of the editor.
  5. Tools → Board → Teensy 4.1, USB Type → Serial, pick the port, and click Upload.
  6. Open the Serial Monitor at 115200 and set the line ending to Newline. Commands only run when a line ends. Type ARM, wait for ARMED, then type LAUNCH.
  7. For the ground station, open ESP32_Ground_Link/ESP32_Ground_Link.ino, install the esp32 by Espressif board package, choose ESP32 Dev Module, and upload it to the ESP32.
